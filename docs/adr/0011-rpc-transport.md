# 0011. RPC transport

**Status**: Accepted
**Date**: 2026-10-29
**Applies to**: `apps/*` (server/client boundary), `src/shared/server/rpc/`, `src/routes/api/`

## Context

A TanStack Start app needs a way for client code to call server use cases. The framework offers
server functions (`createServerFn`): each one is an RPC endpoint generated by the bundler and
bound to the framework's runtime. [ADR 0003](./0003-clean-architecture.md) keeps the
framework at the edge, and [ADR 0010](./0010-app-layout-and-architecture-enforcement.md) puts
each feature's transport in its own `server/rpc/` layer that must be testable without a running
server. The transport also decides how business errors reach the client and how the client
caches data.

## Decision

- **oRPC is the transport.** Each feature exposes its procedures through a
  `create<Feature>Procedures(useCases)` factory in `server/rpc/`. `src/shared/server/rpc/router.ts`
  composes them into one typed router; the composition root builds it with the wired use cases.
- **One endpoint.** The server route `src/routes/api/rpc.$.ts` mounts the router with oRPC's
  `RPCHandler` under `/api/rpc`. No feature declares its own HTTP route.
- **Typed client without server code.** `src/shared/client/rpc-client.ts` builds a
  `RouterClient<AppRouter>` from a type-only import of the router. In the browser it is a
  same-origin `RPCLink` to `/api/rpc`. During server-side rendering it calls the router
  in-process (oRPC's "Optimize SSR" recipe): the composition root registers
  `createRouterClient(router, { context: rpcContext })` on `globalThis.$rpcServerClient`, with
  the same context as the `/api/rpc` handler, and the client module reads it. `src/server.ts`
  imports the composition root first so the client is registered before any route module loads.
  The server never calls itself over HTTP: an HTTP self-call targets the Host the browser used,
  which the server cannot always reach (port-forward, container, reverse proxy), and the page
  then fails to render. Query and mutation options come from `@orpc/tanstack-query`, so loaders
  and ViewModels share one cache.
- **Input validation and error mapping at the boundary.** Each procedure validates its input with
  the feature's zod schema (`schemas.ts`, shared with the client form). One middleware
  (`src/shared/server/rpc/errors.ts`) maps business errors to `BAD_REQUEST` with a stable code
  and every other error to `INTERNAL_SERVER_ERROR` with a reference id.
- **Server functions are not used** for feature calls. They stay available for framework-level
  needs that are not a feature's API, recorded in a new ADR when one appears.

## Alternatives considered

- TanStack Start server functions: rejected. The transport is tied to the framework and its
  bundler, each function is its own endpoint, a function cannot be called in a unit test without
  the framework runtime, and moving a feature to another server (a worker, another framework)
  means rewriting its transport.
- tRPC: rejected. Comparable typed router, but oRPC is framework-agnostic on the server
  (fetch-standard handler), ships a TanStack Query integration and an OpenAPI path from the same
  procedures, and was the maintainer's chosen target.
- Hand-written REST routes with a fetch client: rejected, client and server types drift and every
  route repeats validation and error mapping.

## Consequences

- Procedures are unit-tested by calling the router directly, without HTTP
  (`tests/unit/features/*/rpc/`).
- Adding a feature adds one entry to `router.ts`; the client gets its types at once, with no code
  generation.
- `@orpc/*` stays at the transport edge: `server/rpc/`, `shared/server/rpc/`, `shared/client/`
  and a feature's `client/api/`. Domain and application code never import it; the rules in
  `.claude/rules/clean-architecture.md` state it and review enforces it, since the
  `ARCH-VENDOR` list targets infrastructure SDKs.
- Errors cross the wire as `ORPCError` data (`{ code }` or `{ referenceId }`); the client reads
  them in one place per feature (`client/api/`) and maps codes to copy.
- The app depends on oRPC's release cadence in addition to TanStack Start's; both are pinned
  exactly ([ADR 0005](./0005-dependency-versioning-and-releases.md)).
