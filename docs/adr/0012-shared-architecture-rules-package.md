# 0012. Shared architecture rules package

**Status**: Accepted
**Date**: 2026-10-30
**Applies to**: the repository (`packages/arch-rules`, root `biome.jsonc`, release automation) and
every project created from it

## Context

[ADR 0010](./0010-app-layout-and-architecture-enforcement.md) enforces the app layout and the
`ARCH-*` import rules with Biome overrides, GritQL plugins and a layout test, and
`.claude/rules/` explains them to coding agents. Every project created from the template gets a
copy of all of it. A copy drifts: a rule fixed in the template never reaches the projects, and a
project that edits its copy silently weakens a rule. The rules need one source, versioned, that
projects consume and update like any other dependency.

## Decision

- **One public package** (R4). The rules ship as `@azurioh/arch-rules` from
  `packages/arch-rules`, MIT, with a Biome preset, its GritQL plugins, the agent rules and a CLI.
  Usage is documented in its [README](../../packages/arch-rules/README.md).
- **Biome preset from `node_modules`** (R1). A consumer lists the package as a root dependency
  and extends it by package specifier (`"extends": ["@azurioh/arch-rules/biome"]`). The preset
  file is not named `biome.jsonc`, which Biome would read as a nested root configuration.
- **Plugins by package specifier** (R2). A Biome plugin manifest names each `.grit` rule and the
  preset registers each one as `@azurioh/arch-rules/<rule>`; relative paths resolve against the
  consumer and fail. The specifier form is not documented by Biome, so `@biomejs/biome` is a peer
  dependency and the fixture suite runs through the real package resolution.
- **A project adds rules through GritQL plugins** (R3). A project's `plugins` list is
  concatenated with the preset's, so its own plugins run alongside. A `noRestrictedImports`
  override is allowed only on paths the preset does not cover: on a covered glob it replaces the
  preset's restriction and the `ARCH-*` id disappears.
- **The template consumes the published version** (R5), pinned exactly, never `workspace:*`. It
  behaves like any other consumer, receives update pull requests, and cannot lint with unreleased
  rules. Projects created from the template delete `packages/arch-rules` and its release
  component.
- **release-please releases it, CI publishes it** (R6). The package is a third release-please
  component, `arch-rules`, starting at `1.0.0`. A `publish-arch-rules` job packs it with
  `pnpm pack` and runs `npm publish --provenance` through npm trusted publishing, with no token;
  the first version is published once by hand. A change that can flag previously accepted code is
  a `feat(arch-rules)!` commit (major), a fix that only removes a false positive is `fix`, and
  each commit subject names the affected rule ids so the changelog lists them.
- **Daily Dependabot updates** (R7). The npm entry runs daily with an `arch-rules` group first,
  so a new version reaches consumers within 24 hours.
- **Fixtures and checks** (R8). Every rule id has a violating and a compliant fixture in the
  package, run against a temporary consumer that extends the package by specifier; a missing one
  fails `pnpm check` and blocks the release. `ARCH-LAYOUT` becomes `arch-rules layout`, run in
  the consumer's `check` script. A short parity test stays in the template and asserts every id
  still fires, which catches an override that disables a preset rule.
- **Synced agent rules** (R9). The package ships `rules/*.md`; `arch-rules sync` writes them to
  `.claude/rules/arch-rules/` with a "managed by" header and `arch-rules check` fails on a file
  that differs, is missing or is stale. Files without the header are project-owned and never
  touched. `AGENTS.md` is regenerated by the conventions plugin, and CI's `agents-md` job catches
  a skipped regeneration.

## Consequences

- A rule changes in one place, `packages/arch-rules`, and reaches every project as a reviewed
  dependency update instead of a manual copy.
- A rule change reaches the template's own lint only after it is released: the template switches
  from its local copies to the published version in a follow-up pull request.
- An update can turn a project's CI red when a major version flags existing code; the project
  moves the code or holds the update, never silences the rule.
- The plugin specifier relies on undocumented Biome behaviour; a Biome upgrade that breaks it
  fails the package's tests before any release.
- Open risks: the `@azurioh` npm scope must belong to the maintainer, and Dependabot has not yet
  been observed opening a pull request on this repository's pnpm lockfile; the first release is
  the live test.
